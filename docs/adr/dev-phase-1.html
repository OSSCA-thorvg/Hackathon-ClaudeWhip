ClaudeWhip Development Phase 1 — Architecture & Behavior Details

Phase 1 Development Complete · 2026-08-02 · The rationale for each decision lives in its ADR; this document is a snapshot of "how it actually works right now"

1. What Works

A gameplay slice that is self-contained in the browser works: Claude (the Clawd mascot) characters stand in a vertical line on the right side of the screen, and you move the whip-wielding player with ↑↓←→ and strike with Space. A character that gets hit plays a reaction where it squints its eyes and shakes (no effect on the real session — visual only).

The boundary of phase 1: session data is still mock — session/mock-adapter.ts publishes 3 fake sessions at boot. The bridge server (detecting real active Claude Code sessions) is phase 2 work; its design is settled (ADR-0004) and only the server stub and the protocol's placeholder are in place.

4. Event Bus — a Typed Contract over Pluggable Transports

Implementation: client/src/core/bus/. Contract: shared/src/events.ts.

EventPublisherSubscriberPurpose
session_snapshotmock adapter (cache: true)fetchCached at main's bootsession list → character creation
session_started/ended(phase 2: ws-adapter)(phase 2)session entry/exit
player_moveinput/keyboardlogic workerarrow-key hold state
whip_swinginput/keyboardlogic workerwhip input
game_state_updatedlogic worker (60Hz)render-loop (latest-wins)player x/y/facing/swinging
target_hitlogic workerrender (the target in question)hit-reaction trigger

Core mechanisms:

  • Transport abstraction: LocalTransport (same thread) + PortTransport (worker MessagePort). Components never touch postMessage directly
  • Handler isolation: every subscription callback is wrapped in try/catch so the dispatch loop never dies
  • High-frequency handling: for game_state_updated, the render loop overwrites only the latest value in the handler and applies it once in rAF (latest-wins), setting latest = null after applying to prevent double application
  • late-joiner cache: events published with cache: true are retained keyed by event name — a component created later gets the last state immediately via fetchCached(name)

5. Boot Sequence (client/src/main.ts)

  1. Inject layout CSS variables (--column-width, --floor-inset — the single source is render/layout.ts)
  2. Create the Bus
  3. Start the mock session adapter → obtain 3 sessions via fetchCached('session_snapshot')
  4. Stage.create() — initialize thorvg 'gl' (local WASM), a single canvas, add a TargetNode per session plus the PlayerNode as Scenes, and pre-place them at their spawn positions
  5. Start the logic worker — connect the bus over a MessageChannel (PortTransport), pass the initial geometry through the control channel
  6. Bind the keyboard → start the single rAF render loop

6. Rendering — Single Canvas + Scene per entity ('gl')

Implementation: client/src/render/. Rationale: ADR-0006 (supersedes 0005).

  • There is exactly one canvas on the page (#stage-canvas, the full viewport). The WebGL2 context was confirmed empirically. Only the background decoration (#backdrop) and the text (session labels, HUD — #overlay) are DOM
  • Character = Scene node: LottieNode owns a Scene + LottieAnimation pair. Position and horizontal flip are applied by place(cx, cy, flipX) via a matrix — thorvg's scale() is isotropic only, so flipping goes through a Matrix, and the pivot is the manifest's bodyCenter (see the CLAUDE.md pitfalls)
  • State transition = Lottie marker segment: idle loop ↔ playOnceThenIdle('hit'|'swing'). Frame seeking happens in our own rAF (Animation.play() is forbidden; guard against re-setting the same frame)
  • One raster per frame: Stage.renderFrame(dt) advances each node's frame and then calls canvas.update().render() exactly once
  • Layout is computed in code (layout.ts): session slots are stacked in a 240px column on the right, and the resulting coordinates are converted into the worker contract by toStageGeometry(). On resize: canvas.resize + recompute + resend

7. Game Logic — 60Hz Simulation in a Web Worker

Implementation: client/src/game/. Rationale: ADR-0003 (thorvg does not support worker rendering → only the logic is split out).

  • Pure-function simulation (simulation.ts): (state, input) → next state. No contact with DOM/worker APIs — testable without a worker
  • Fixed tick: a 60Hz accumulator loop (logic.worker.ts). The worker cannot see the DOM, so geometry is injected by main through the control channel (the init/geometry messages in protocol.ts) — separate from bus traffic
  • Movement: 4-directional at 300px/s, with the body center clamped 40px inside the stage margin. Only left/right input changes facing
  • Swing state machine: re-input is ignored until the 30-tick playback (0.5s, mirroring the length of the asset's 'swing' marker) completes. Detection runs exactly once, on entering ticks 8–20 (the interval where the whip is extended)
  • Hit detection (hitbox.ts, refined in phase 2): AABB overlap of the crack frame's whip box (measured from the asset FK, manifest whipStrikeBox) × the target's body box — every overlapping target is hit, excluding targets already in a reaction. The 30-tick hit reaction doubles as the re-hit cooldown

8. Asset Contract — a Replaceable Clawd Character

Implementation: client/public/assets/characters/*.json + client/src/assets/manifest.ts.

  • A boxy Clawd mascot (based on the user's sketch): a 2:1 horizontal body (#D97757) + dot eyes + side arms + legs. The player adds an 8-bone chain whip (dark handle + orange lash)
  • Marker convention: target idle (0–60 loop) / hit (60–90), player idle / swing. Loop seams and return poses are verified at the pixel level
  • The manifest is the single source: file paths, marker names, canvasSize (target 240 / player 360 — the whip's headroom), bodyCenter (target 120,120 / player 104,255 — the reference for alignment, flip pivot, hitbox, and spawn). Replacing an asset = changing only the JSON file + the manifest values
  • ⚠️ If you change a marker's length, change the tick constants in simulation.ts (SWING_TICKS, etc.) along with it — see the manifest comments

9. The Path a Single Strike Travels (end-to-end)

[keydown Space]
  input/keyboard ──▶ bus.broadcast('whip_swing')
                       ├─ LocalTransport → (main subscriber: render-loop consumes the state for swinging edge detection)
                       └─ PortTransport → logic worker
  Worker's next tick: applySwing → swingTick=0 begins
  Tick 11 (entering the crack): pickHitTargets(whip box, targets) → 'mock-bravo' hit!
    ├─ bus.broadcast('target_hit', {sessionId}) ──▶ main: TargetNode('mock-bravo').playHit()
    │                                               → hit marker segment once + scene shake + label is-hit
    └─ target hitTick=30 begins (excluded from re-hits during the reaction)
  Every tick: bus.broadcast('game_state_updated', {player, targets})
    ──▶ render-loop: refresh latest → in rAF, PlayerNode.place(x,y,flip) + swing segment
  Every rAF: Stage.renderFrame → advance every node's frame → canvas.update().render() once

11. What Remains (phase 2)

  • Implement the bridge server: session-monitor (ps scan + jsonl mtime + SDK, 1-second polling) → WebSocket push. On the client, replace the one line for the mock adapter in main.ts with ws-adapter (the published events are identical)
  • When swapping in ws-adapter, make boot reactive: it currently relies on the mock's synchronous cache — switch to rebuilding from a session_snapshot subscription + consuming session_started/ended (reviewed and settled; to be done together with the server integration)
  • Polish (optional): staggering the phase of the targets' idle (currently everyone blinks in sync), sound, differentiated animation per working/idle state
