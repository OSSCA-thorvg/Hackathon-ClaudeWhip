ADR-0007: Server-Optional Client — Manual Connection + Reactive Session Lifecycle

Accepted · 2026-08-02 · Author: ticket 011 session

Context — why this decision is needed

This game is deployed on static hosting such as GitHub Pages. The bridge server that detects sessions (ADR-0001), on the other hand, runs only on the player's own machine, and only the person who started the server knows its address. In other words, the client must satisfy the following two things at the same time.

  • It must open and be playable even without a server (there is just nothing to hit).
  • When a server does appear, characters must show up without reloading the page.

The previous boot sequence could do neither. That is because main.ts read bus.fetchCached('session_snapshot') synchronously at boot time and built the stage from that list. That structure only held up because the mock adapter published the snapshot within the same tick — a real snapshot arriving from across the network shows up after boot, so it always started with 0, and sessions that arrived afterwards were never on screen.

Decision — what was decided

  1. Do not auto-connect. The user has to enter the bridge address in the top bar of the screen and press the connect button for it to attach. The default value is ws://localhost:{BRIDGE_PORT}, but it is nothing more than a pre-filled default.
  2. The stage boots with 0 targets. Session membership arrives entirely through bus events: session_snapshot (full reconciliation) / session_started (add one) / session_ended (remove one). Every time membership changes, the layout is recomputed and geometry is re-sent to the worker.
  3. When the connection drops, the targets disappear too. The adapter publishes an empty snapshot at the moment of socket close / user disconnect.
  4. Connection state is announced through the bus event server_connection_changed (added to the EventMap). The server does not send this event — it is a client-only event that is not in ServerEventName.
  5. Entrance/exit presentation is done only with scene transform/opacity: pop-in (scale 0→1, easeOutBack, 260ms) / fade-out (200ms, slight shrink). No separate rAF and no CSS animation is created — the existing renderFrame(dt) advances it.

Rationale — why it was done that way

Manual connection: If, on static hosting, it tried to attach to localhost:8787 automatically, a connection failure would be printed in the console of every single visitor who did not start a server, and backoff retries would spin forever. There is no reason for someone who came to see the demo to have an error log as their first impression. On top of that, the very look of a page opened on someone else's machine scanning their local ports is undesirable.

Removing targets when disconnected: In this game, one character means "one Claude Code session alive on this machine right now." If characters remain after the server has died, that one and only meaning becomes a lie — you would effectively be hitting sessions that have already ended. It is more honest to clear it out than to leave stale data. If reconnection succeeds, the server sends a snapshot immediately upon connection, so the characters come back with a pop-in. (Measured: killing the server process → state disconnected + label removal in about 200ms, followed by backoff retries. On server restart, it recovers automatically without a click.)

Why state flows through the bus: If the connection UI subscribed to the adapter directly, either the adapter would have to know about the UI or the UI would have to know the adapter's internals. State is emitted as an event and the UI looks only at that — that way transitions that the UI did not initiate, such as backoff retries, are displayed automatically (exactly the boundary rule of ADR-0002).

Alternatives — considered but rejected

  • Auto-connect at boot (+ silently ignore failures) — console noise and pointless retries. For the vast majority of static-hosting visitors there is no server at all.
  • Keep the last session list even when the connection drops — the screen keeps looking plausible but diverges from reality. It breaks the game's premise of "sessions alive right now."
  • Keep the mock adapter as a demo mode — now that the real server works, fake sessions are harmful because they are indistinguishable from real data during a demonstration. The right answer for a demo without a server is "no targets."
  • Pass connection state through a callback — direct adapter↔UI coupling. Adding one more event to the bus contract is more consistent with the rules.

Consequences — the results of this decision

  • The concept of "the session list at boot time" is gone from main.ts. The dependence on synchronous fetchCached has disappeared, and a late-arriving snapshot is a normal path.
  • Stage membership changes are asynchronous (Lottie loading), so they are serialized through an internal queue. Even if a snapshot and a started event overlap, the slot order does not get inverted. Slot order is first-come order, not the server snapshot order — even if the list is reordered, characters do not swap places.
  • Re-sending worker geometry only happens when membership actually changed. It is safe because withGeometry preserves the reaction progress of live targets.
  • Target paints are not added to the canvas directly but to the target layer Scene. That way, no matter how many targets come and go, the player (the whip) always stays on top — detaching and reattaching the player paint to preserve ordering would be a dangerous thing that relies on refcounts.
  • Revisit condition: if we come to support a remote (non-localhost) bridge, we need to revisit address persistence (localStorage) and wss/authentication. For now we deliberately do not persist it.
