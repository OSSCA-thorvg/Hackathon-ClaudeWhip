ADR-0009: Testing Strategy — Pure-Module Units + Fake-Bridge E2E

Accepted · 2026-08-04 · Author: seungwon (ticket 017)

Context — why this decision is needed

Up to the point where the second development round was completed, there were 0 tests. And yet the things to be verified in this project split into extremes in character: on one side there is pure logic that can be run as-is in Node (simulation, hit detection, layout, camera, label folding, event bus, ps parsing), and on the other side there is a layer that cannot be executed at all without a browser (the thorvg WASM+GL renderer, the WebSocket adapter, the worker boundary). On top of that, the actual data source — the bridge server — depends on the live Claude Code sessions on this machine: if a test attaches to the real server, the session count varies from moment to moment, making it non-deterministic.

Decision — what was decided

  • A split between units (Vitest) and E2E (Playwright). Units cover only pure modules — they are all environment: 'node', and if a DOM environment appears to be needed, the target selection was wrong. The browser-coupled layers (renderer, adapter, worker wiring) are all covered by E2E.
  • The session source for E2E is a fake bridge WS server (e2e/fixtures/fake-bridge.ts). The test starts it itself and injects session_snapshot at arbitrary points in time — it does not depend on the real server or real sessions, so it is deterministic, and since the framing shares shared's wireFrame() with the real server, it is structurally guaranteed that a fake frame is byte-for-byte identical to a real frame.
  • The observation window for E2E is the dev build's window.__claudewhip debug handle — it does not look at canvas pixels. The handle's shape has been promoted to the client-owned type ClaudeWhipDebug (client/src/debug-handle.ts), and e2e imports the same type, so if the handle's composition changes, pnpm typecheck catches it. That is why E2E must target the vite dev server (the production bundle does not have the handle).
  • What tests verify is the contract — no copies. Expected values are not copied numbers; they are derived from the source (assets/manifest.ts, each module's exported constants). To make this possible, the simulation tuning constants, WHIP_STRIKE_OFFSET, the hit-band back-calculation (hitBand) and so on were promoted to exports — if the assets are re-measured, the tests follow automatically.
  • For the server, only the pure part is unit tested — parseClaudeProcesses and the detection rules, with fixtures of actually measured ps output. The SessionMonitor polling loop does not get an exec/fs injection refactor.
  • CI is out of scope this time — only up to local pnpm test / pnpm test:e2e. The CI workflow will be decided together with the GH Pages deployment pipeline (an undecided ticket).

Rationale — why it was done that way

  • The boundary between pure and coupled has already been drawn by the architecture (ADR-0002 event bus, ADR-0003 worker separation, "keep the simulation as pure functions"). If the test structure follows that boundary as-is, mocks and stubs are barely needed.
  • Thanks to the server-optional design (ADR-0007), client membership is entirely event-driven — as long as the fake bridge pushes things in the same order as the real server (snapshot immediately on connection, started→ended→snapshot), the client cannot tell the difference. A real-server smoke test would add almost no extra confidence.
  • The debug handle was made in the first place "so that the console and E2E can verify state without looking at the canvas with their eyes" (ticket 011) — introducing E2E is the realization of that purpose, and the type promotion turns drift in the observation contract into a compile error (demonstrated by a field-rename experiment).
  • Verification figures: 166 unit tests (8 files, ~170ms), 9 E2E tests (4 specs, ~7 seconds). E2E stability was confirmed with 5 consecutive runs + repeat-each=3 + workers=1. While writing them, it was established that the hit band numbers from ticket 012 were based on the v1 assets — the current (v2) values are the band [cy−41.5, cy+78.5] and an active window of 14~19 ticks, and this discovery is itself the justification for the "no copied numbers" principle.

Alternatives — considered but rejected

  • Real-server smoke E2E — non-deterministic because it depends on the number of real sessions on this machine, and impossible in CI. Excluded by user decision.
  • node:test — it has no dependencies, but the TS loader, watch mode and reporting are cumbersome, and Vitest is the coherent fit for a vite 8 project.
  • Renderer unit tests in a jsdom-style DOM environment — thorvg is WASM+GL, so it cannot run there anyway. Most of the CLAUDE.md pitfalls are of the "verify in a browser" kind, so renderer verification is E2E's job.
  • Reviving a client-embedded mock adapter — we do not resurrect, in the name of testing, what was deleted in ticket 011. Fakes live outside production code (in e2e fixtures).
  • A SessionMonitor injection refactor — excluded because the deformation of production code is large relative to the coverage gained.

Consequences — the results of this decision

  • What we gain: a deterministic test suite (green anywhere locally), regression defense for the hit geometry and detection rules, type safety for the observation contract. 0 changes to production behavior (only export promotions and pure additions).
  • What we accept: the real-server path (ps/lsof/SDK polling) has no automated test — regressions that break session detection depend on manual verification (pnpm dev). Since E2E presumes the dev server, the production bundle itself has no smoke test.
  • Revisit condition: when building the GH Pages deployment pipeline, decide on CI execution (and whether to smoke-test the production build). If logic grows at the worker boundary or in the adapter, redraw the boundary of what to pull down into units.
