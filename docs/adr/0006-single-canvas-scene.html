ADR-0006: Single canvas + Scene per entity + 'gl' renderer

Accepted · 2026-08-02 · Author: ticket 008 HITL session · Supersedes ADR-0005

Context — why this decision is needed

While reviewing the prototype (one canvas per session, ADR-0005), the user's original intent was confirmed: REQUIREMENT's "draw using as many webcanvases as there are" meant drawing N characters inside one large canvas, and the request for worker/OffscreenCanvas optimization also presupposed the full re-render cost of a single canvas. Splitting the canvas was a misreading of the requirement.

Decision — what was decided

  • One canvas covering the entire game area. Characters (N targets + the player) go into the scene graph as thorvg Scene nodes, and their positions are controlled with paint translate()
  • Switch the renderer to 'gl' — with only one canvas, the reason ADR-0005 chose 'sw' (a WebGL context consumed per canvas → the browser cap) disappears. In a structure that redraws the whole screen every frame, GPU rasterization is effectively mandatory
  • The right-hand vertical single-file layout comes not from CSS but from layout computation in the render layer — slot coordinates are passed to the worker via the existing protocol's geometry message (contract unchanged)
  • Session labels and the HUD stay as a DOM overlay on top of the canvas (text crispness, accessibility)
  • Retained: Lottie marker segment state transitions, ?url+locateFile WASM loading, the single rAF loop, and the ban on Animation.play() — the items validated in ADR-0005

Rationale — why it was done this way

  • User intent (the authoritative reading of the original requirement)
  • On a single canvas every character's idle animation runs continuously, so a full re-render each frame is unavoidable — per-canvas dirty-flag localization becomes meaningless, and drawing everything on the GPU ('gl') is the right call
  • Session entry/exit is handled by Scene node add/remove + dispose (equivalent cost to DOM add/remove)
  • Separating game logic into a worker (ADR-0003) remains valid — the greater the render load, the more valuable it is to have taken the simulation off the main thread

Alternatives — considered but rejected

  • Keeping one canvas per session (ADR-0005) — a misreading of the requirement. It had technical merits (CSS layout, localized rasterization), but it was not the picture the user wanted
  • Single canvas + 'sw' — software-rasterizing a viewport-sized area (several MP) at 60fps is a risk on a hackathon demo machine. Kept only as the fallback if 'gl' fails
  • Moving rendering into a worker via OffscreenCanvas — unsupported by thorvg, ADR-0003 stands

Consequences — results of this decision

  • Reimplementation of the render layer (character-canvas/player-canvas/render-loop) — the bus contract, worker, and input are unchanged
  • The switch to 'gl' opens the possibility of new pitfalls (context lost, gl-specific bugs) — record them in CLAUDE.md's pitfalls when found
  • On resize, canvas.resize() + layout recomputation + geometry re-transmission are required
  • No matter how much the session count grows, it becomes irrelevant to the context cap (the scale ceiling is GPU rasterization performance)

Amendment — the background decoration goes into the canvas too (2026-08-03, ticket 015)

The original decision moved only the characters to the canvas and left the background decoration as a DOM layer beneath the canvas (#backdrop: stage gradient + session column background/dividers). As the user pointed out, this only half-honored this ADR's premise that "the entire game area is one canvas" — the same number, the column width (240px), was split between render/layout.ts and a CSS variable, and on resize the canvas and the DOM updated independently, leaving room for them to be off by one frame.

  • The background moves to the bottommost layer of the scene graph — render/backdrop.ts owns a Scene that draws the full viewport rectangle (linear gradient) + session column rectangles + 1px dividers, and Stage adds it to the canvas first. The #backdrop markup and the --column-width CSS variable are deleted
  • Text stays in the DOM (session labels · HUD · connection bar). The hinting quality of 11px monospace, cursor blinking (CSS animation), font loading, ellipsis based on measured character widths — DOM/CSS is overwhelmingly better at all of these, and moving them to the canvas would only lose ground. In other words, this ADR's "one canvas" reads as drawings on the canvas, letters in the DOM
  • The price paid: thorvg cannot read CSS variables, so 5 background colors exist in duplicate in :root of styles.css and in render/backdrop.ts. Comments pointing at each other have been added on both sides. CSS's elliptical radial-gradient could not be carried over as-is to thorvg's circular gradient, so it was approximated with a vertical linear one
