ADR-0003: Worker Strategy — Rendering on the Main Thread, Game Logic in a Worker

Accepted · 2026-08-02 · Author: wayfinder charting session

Context — Why this decision is needed

REQUIREMENT calls for making maximum use of workers for optimization, and for analyzing the feasibility of using OffscreenCanvas and implementing accordingly. Research (.wayfinder/tickets/002) showed that @thorvg/webcanvas@1.1.0 does not support OffscreenCanvas/worker rendering:

  • The Canvas constructor accepts only a CSS selector and calls document.querySelector internally — DOM required
  • OffscreenCanvas appears 0 times in the bundle source, and window.devicePixelRatio is accessed directly
  • Official issues #225 (request for OffscreenCanvas initialization, open), #227 (maintainer: "web worker based rendering is not supported"), #287 (DOM-less interface roadmap, open)

Decision — What we decided

ThreadResponsibilityCode location
Main threadAll thorvg rendering (canvas, Lottie frame seeking, rAF loop) + key input + WebSocketclient/src/render, input, session
Logic worker (1)Game simulation at a fixed 60Hz tick: player movement, whip state machine, hit detectionclient/src/game

Worker→main communicates only via the game_state_updated event (with coalescing applied). The thorvg /thread build (pthread parallelization inside the engine) is not adopted.

Rationale — Why we did it that way

  • Since OffscreenCanvas is impossible at the library level, the feasible form of "maximum worker utilization" is separating the simulation — the main thread becomes drawing-only, so input latency becomes independent of logic cost
  • Reasons for excluding the /thread build: new in 1.1.0 and unstable (#329), requires COOP/COEP headers (breaks embedding of external resources), packaging defect (the pthread worker references files that are not shipped) — no benefit relative to the hackathon risk
  • The render load itself is small: as many small canvases as there are sessions (a few to a dozen-odd) + the 'sw' renderer (ADR-0005)

Alternatives — Considered but rejected

  • OffscreenCanvas + worker rendering — Impossible because thorvg does not support it. Revisit when #287 is resolved
  • thorvg /thread build — The risks above. Revisit if a performance bottleneck is measured
  • Everything on the main thread — It would work, but it would abandon REQUIREMENT's intent to make use of workers. Separating the logic worker is low-cost and has structural benefits (pure-function simulation, easy testing)

Consequences — Results of this decision

  • Never move the render code into a worker — the DOM dependency in render/ is intentional
  • Keep the simulation as pure functions (simulation.ts) — unit-testable without a worker
  • When thorvg.web #225/#287 are resolved, revisit this ADR and discuss migrating to OffscreenCanvas
