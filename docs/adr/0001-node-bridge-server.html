ADR-0001: Two-Tier Architecture — Node Bridge Server + Browser Client

Accepted · 2026-08-02 · Author: wayfinder charting session

Context — Why this decision is needed

REQUIREMENT calls for an app that "runs in the browser" to check the number of currently active sessions using @anthropic-ai/claude-agent-sdk. However, research (.wayfinder/tickets/001) showed the SDK cannot run in a browser: it is a Node.js-only library that spawns the claude CLI as a subprocess and communicates over stdio. Furthermore, session detection itself requires access to the local filesystem (~/.claude/projects/) and to the process list, which is fundamentally impossible inside the browser sandbox.

Decision — What we decided

Split the app into two tiers:

TierPackageRole
Bridge server (Node) packages/server Owns the Agent SDK. Detects active sessions (1-second polling) and pushes session snapshots/changes over WebSocket (:8787)
Client (browser) packages/client Vite app. Receives WebSocket → event bus → rendering/game logic. Never imports the SDK

The two share only the types in packages/shared (SessionInfo, the event contract). The default communication direction is a one-way server→client push (hits are visual effects only, so no client→server commands are needed, .wayfinder/tickets/004).

Rationale — Why we did it that way

  • The official SDK hosting documentation presents exactly this structure (SDK on the backend + streaming to the browser over WebSocket/SSE) as the standard (hosting docs)
  • The ps scan and file mtime lookups needed for session detection are only possible in Node anyway (ADR-0004)
  • Choosing WebSocket: the reconnection-handling code is comparable to SSE, and it leaves room to expand if bidirectional communication becomes necessary later

Alternatives — Considered but rejected

  • Browser only (using the SDK directly) — Technically impossible. The SDK depends on subprocesses/the filesystem
  • Static file polling (a file server without an app server) — ~/.claude is outside the web root and process detection is impossible, so "active" cannot be determined

Consequences — Results of this decision

  • Development/demo requires running 2 processes → the root npm run dev runs them simultaneously via concurrently
  • The client must keep working even if the server dies (reconnect backoff) — demo safety
  • The server is for this machine only (localhost bind) — security considerations can be kept minimal
