ADR-0004: Active session detection — ps process scan + session file mtime + SDK

Accepted · 2026-08-02 · Author: wayfinder charting session

Context — why this decision is needed

The scope of "sessions currently in use" was decided as active Claude Code sessions running on this machine (.wayfinder/tickets/006, user decision). The SDK's listSessions() returns every past session in the directory, so a separate criterion is needed to pick out only the sessions that are "alive right now".

Decision — what was decided

We combine three sources (all empirically verified on this machine, .wayfinder/tickets/001):

  1. Liveness determination: extract the session ID from ps output — a running process is itself the evidence of an active session. The regex lives in a single source of truth: the SESSION_PS_PATTERN constant in session-monitor.ts. (⚠️ This step 1 was replaced on 2026-08-03 by the Amendment (detection v2) — see below. SESSION_PS_PATTERN no longer exists.) 
    ps aux | grep -oE 'claude --session-id [a-f0-9-]+' | awk '{print $NF}'  # example as of time of writing
  2. Metadata enrichment: match the session ID against ~/.claude/projects/<encoded-cwd>/<session-id>.jsonl to restore the cwd (non-alphanumeric characters in the path are replaced with -), and obtain summary/gitBranch via the SDK's getSessionInfo()
  3. Status distinction: if the .jsonl mtime is within WORKING_THRESHOLD_MS (10 seconds at time of writing), it is working, otherwise idle — usable for differentiating character animations

Polling runs at a POLL_INTERVAL_MS (1 second at time of writing) interval. Diffing against the previous snapshot generates session_started/session_ended events. The current values of the tuning constants have a single source of truth: packages/server/src/session-monitor.ts.

Rationale — why it was done this way

  • Process existence is the only reliable signal of "active" — file mtime alone cannot distinguish a terminated session from a quiet one
  • Empirical evidence: on this machine, the ps scan extracted the IDs of 2 active sessions directly from the command line
  • 1-second polling amounts to a few dozen ps + stat calls — negligible load, and simpler than adding a file-watcher dependency (chokidar, etc.)

Alternatives — considered but rejected

  • SDK listSessions() alone — returns all past sessions too, cannot determine liveness
  • File watching (fs.watch) — mtime updates only tell you "working", not that the session is alive. As a diff source, polling is simpler
  • Searching for lock files — no guarantee that Claude Code exposes a per-session lock (private implementation detail)

Consequences — results of this decision

  • The ps command-line format (the --session-id flag) depends on Claude Code's internal implementation — a version bump could break it, so the pattern is isolated as a constant in session-monitor.ts
  • macOS/Linux only (depends on ps) — Windows support is out of scope
  • Detection itself works even without the SDK (steps 1 and 2) — the SDK is only for metadata enrichment, so graceful degradation is possible on failure

Amendment (2026-08-03) — detection v2: including processes without a session ID

Ticket .wayfinder/tickets/016-session-detection-v2.md · This does not overturn the decision; it only extends step 1 (liveness determination).

What the problem was (measured on this machine). v1's SESSION_PS_PATTERN matched only claude --session-id <uuid>. But the only sessions that carry a session ID on the command line are sessions launched as background tasks. Most of the sessions the user was actually working in were not caught:

  • Interactive sessions — of the form claude --settings {…} (e.g. PID 11321, cwd ~/Documents/some-project)
  • VS Code extension sessions — …/anthropic.claude-code-*/resources/native-binary/claude --output-format stream-json … (e.g. PID 77090, same cwd)

Neither process keeps the transcript (.jsonl) open at all times (it opens and closes only when writing), so the session cannot be traced back via open files. On the other hand, lsof -a -p <pid> -d cwd always yields the working directory.

The v2 algorithm. One ps call → candidate selection → ID assignment:

  1. Candidate selection is done by the executable (argv[0]) only — string-matching the whole command line catches other people's processes that happen to have 'claude' in their arguments (cmux hooks, shell wrappers, our own pnpm/vite filters). Only processes whose basename is exactly claude are candidates (case-sensitive — /Applications/Claude.app/…/Claude and Claude Helper are eliminated here).
  2. Exclude infrastructure roles: if argv[1] is bg-spare, bg-pty-host, daemon, mcp, doctor, update, install, migrate-installer, setup-token, or plugin, it is not a session (INFRA_SUBCOMMANDS). A bare argument not in this list is treated as a session — because claude "prompt" is a legitimate one-shot session.
  3. Command-line ID: if the token after --session-id or --resume is a UUID, use it as the session ID (SESSION_ID_FLAGS). Including --resume is an extension over v1 — interactive sessions launched with cmux take this form, and the resumed session ID is that process's session ID.
  4. Keep sticky assignment: even without a command-line ID, if a session ID has already been assigned to that pid, reuse it without re-resolving. The cwd mapping below is a guess ("the most recent file in that directory that is not yet taken"), so re-running it on every poll makes a character's identity waver when file mtimes change. The only exception is synthetic IDs (next item) — every SLOW_RETRY_INTERVAL_MS (10 seconds) the assignment is released and promotion to a real session ID is retried. The same 10-second interval is shared by SDK metadata re-lookup, transcript re-resolution, and lsof failure retries (all for the same reason: "let's try again around the time the SDK fills in the cwd hint").
  5. cwd mapping fallback: if nothing above matches, get the cwd via lsof, run encodeProjectDir(cwd) → scan that project directory's .jsonl files newest-first, and use the name of the first file not already claimed by another live session as the session ID. If two processes share the same cwd (measured: interactive + VS Code in the same directory), they take different files in newest-first order.
  6. Synthetic ID: if there is still no matching transcript, emit the session anyway as pid-<pid>. Since the requirement is "as many characters as there are active sessions", a just-launched session that has no transcript yet must still get a character. A synthetic ID is not a real session ID, so it does not perform an SDK lookup (avoiding meaningless failure logs) and is sent down with lastActivityAt=0 / idle. If a later poll promotes it to a real ID, it is swapped out via session_ended + session_started.

Step 2 (metadata enrichment), step 3 (mtime status distinction), and diff/snapshot are unchanged. The cwd is now filled in the order SDK → lsof → transcript directory name (since the lsof value is measured from the process, the label survives even when the SDK fails).

Cost and failure handling. lsof is called once for a batch of unresolved pids (-p pid1,pid2,…), and the result is cached for the lifetime of the process — claude does not chdir while running. So in steady state there are 0 lsof calls per poll. The call is wrapped in an execFile timeout, and on failure only those pids are left unresolved for this poll (partial output is salvaged and used). Failed pids are negatively cached and retried only every SLOW_RETRY_INTERVAL_MS — since the lsof timeout (3 seconds) is longer than the poll interval (1 second), without throttling a single unresolvable pid would keep piling up subprocesses. Session ID assignment is sticky to the pid so that character identity does not waver from poll to poll.

Empirical evidence (2026-08-03, this machine). v1 reported only 2 sessions (= background tasks that had --session-id). v2 matched exactly: 8 claude session processes counted by ps and 8 in the snapshot — 4 interactive, 1 VS Code extension, 1 bare claude, 2 with --session-id. bg-spare/bg-pty-host/daemon run/Claude.app helpers were all excluded, and our own pnpm/vite processes were not caught either.

New fragility. v1's "dependence on the --session-id format" has grown into three branches — ① install path / executable name, ② infrastructure subcommand names, ③ the transcript filename = session ID convention. All three are Claude Code internals, so if detection breaks, first check CLAUDE_CLI_BASENAME / INFRA_SUBCOMMANDS / SESSION_ID_FLAGS at the top of session-monitor.ts (these replace v1's single SESSION_PS_PATTERN constant). Also, the cwd mapping is a guess, so if several old sessions and a new process are mixed in one directory, a process may get attached to the wrong (but same-directory) session ID — the character count is still right and the cwd in the label is also right; what can be wrong is the summary/branch.
