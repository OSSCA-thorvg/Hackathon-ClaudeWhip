ADR-0005: Rendering strategy — one canvas per session + 'sw' renderer + Lottie markers

Superseded · 2026-08-02 · Author: wayfinder charting session · Superseded by ADR-0006 (single canvas + Scene per entity) — the prototype review confirmed that the user's original intent was a single canvas. The Lottie marker and WASM loading items remain valid in 0006 as well.

Context — why this decision is needed

REQUIREMENT: draw them in a line on the right "using as many webcanvases as there are" sessions. Constraints confirmed in the thorvg research (.wayfinder/tickets/002): the WASM module is a per-page singleton, and the renderer backend (sw/gl/wg) is decided globally, once at init(), and 'gl' consumes a WebGL context per canvas, hitting the browser cap (~8–16).

Decision — what was decided

  • Canvas composition: one small canvas per session (right-hand column) + one player stage canvas. ThorVG.init() is called once, and all canvases share the WASM module
  • Renderer: adopt 'sw' (software) globally — safe even when the number of sessions exceeds the WebGL context cap
  • WASM loading: import wasmUrl from '@thorvg/webcanvas/dist/thorvg.wasm?url' + locateFile — the package default (loading from the unpkg CDN) is forbidden
  • Driving animation: instead of Animation.play(), do anim.frame(f); canvas.update().render() in a single rAF game loop
  • State transitions: switch between markers inside a single Lottie file (idle/hit/swing) via LottieAnimation.segment(marker). The mapping exists only in assets/manifest.ts (assets must be replaceable — .wayfinder/tickets/005)
  • Memory: when a character exits because its session ended, explicitly call animation.dispose() + canvas.destroy()

Rationale — why it was done this way

  • A canvas per session is REQUIREMENT's explicit demand, and it is natural for handling session entry/exit at the DOM level. The official benchmark drives 28 simultaneous instances, so scale is not a concern
  • Choosing 'sw': since there is only one global renderer, it must be decided based on the most constrained use case (many small canvases). On small canvases the performance difference is also negligible
  • Single rAF loop: frame synchronization and pause control are simpler than N per-canvas play() loops, and it combines naturally with game_state_updated coalescing
  • Forbidding the CDN default: removes the only external dependency that would instantly kill an offline / unstable-network demo environment

Alternatives — considered but rejected

  • One large canvas + Scene per entity — could be better for performance, but conflicts with the "as many webcanvases as there are" requirement and prevents leaving layout to CSS. To be revisited if performance problems are measured
  • The 'gl' renderer — context cap risk. The demo could break with 8 or more sessions
  • The @thorvg/lottie-player web component — convenient autoplay, but it lacks direct frame control, marker segments, and HUD compositing, so it is unsuitable for a game
  • Separate Lottie files per state + picture swapping — kept as a fallback in case we end up using assets without markers (the manifest structure accommodates both)

Consequences — results of this decision

  • optimizeDeps.exclude: ['@thorvg/webcanvas'] is mandatory in the Vite config (the Emscripten glue's import.meta.url issue)
  • Character assets must include idle/hit (target) and idle/swing (player) markers — otherwise switch the manifest to the separate-files approach
  • Known bug workaround: calling frame(0) before play() raises an error (thorvg.web#216)
  • If the session count grows to a scale of several dozen, revisit 'gl' + a single canvas
